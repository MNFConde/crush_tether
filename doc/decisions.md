## D-01 命令知识库框架

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「命令知识库（bucket 框架，定稿）」](design.md#命令知识库bucket-框架定稿) |

**背景**：设计评审暴露两类「命令约定关联」问题——等价方言（`npm exec`/`npm x` ≡ `npx`，一处挡一处放即绕过）与双桶冲突（`git reset` 同时落在 confirm/deny 两桶）。初版方案把 alias 表与冲突校验放进用户 `rules.toml`；用户指出这类联系是通用事实而非个人策略，不应由用户配置承载，且预见后续还会出现更多此类关联，要求以可扩展机制纳入。

**决策**：独立**命令知识库**（bucket 框架）——只记录事实（读写属性/别名/联系），不产生裁决；随软件分发 main（scoop bucket 式：可增/删/换源，含官方 main，社区/团队可维护）；格式为紧凑 TOML（一命令一表头，`sub`/`flag` 点号键 + 单行 inline table）；**条目开放、谓词封闭**（槽位种类由引擎版本定义，一类槽位 = 一个消费机制）；**运行时只消费等价类**（alias_of/same_flag/takes_value 归一），属性类只进 lint 与脚本数据源；删光 = 不做语义检查（lint 降级纯结构、判定不受影响）。

**依据**：

- **职责分离正确**：`npm exec ≡ npx`、curl 带 `-o` 会写，是对所有用户一致的客观事实；放行策略才是偏好——通用事实放用户配置属类别错误。
- **知识可独立更新**：新工具出新别名时更新 bucket 即可全员送达；埋在用户配置（含默认生成模板）里，已生成的项目文件永远跟不上——这是分散方案的结构性缺陷。
- 用户配置只剩纯策略，与「配置保持简洁」原则一致；scoop bucket 模式（git repo 即源、增删管理）成熟可借鉴，团队可维护内部工具 bucket。

### 被否决的替代方案

> [!CAUTION] 【已否决】 被否决的替代方案
> 原因：详见下列各项
>
> - **alias 表放用户 rules.toml**：通用知识分散化，社区无法更新已生成的项目配置；用户误删别名即产生放行洞。
> - **JSON 格式**：不能写注释——对社区维护、需讲清槽位含义的知识文件是硬伤。
> - **YAML 格式**：新引依赖 + 缩进陷阱，与 rules.toml 双格式并存增加心智负担；TOML 紧凑问题已由点号键布局解决。

**影响**：默认包不再含 alias 条目；flag 双配原则收窄为 `same_flag` 闭包（design.md 更正登记第 8 条）；裁决日志新增 `kb` 字段与 `type:"load"` 事件行；两态子命令判定的知识来源从默认脚本硬编码下沉为知识库 `write_tokens`/`write_arg_count` 数据；多 bucket 管理与编写时提示登记为 P4 后专项。

## D-02 字段级继承合并模型

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「层间合并（字段级继承，定稿）」](design.md#层间合并字段级继承定稿) |

**背景**：草案 v1 的 merge 语义留下空洞——头部裸列表跨层是「整表覆盖」还是「合并」未定义；「整表覆盖」下项目层想给用户层 allow 列表加一个命令必须全量复制（抄漏即静默改判）。讨论中「挪桶表删除」（把命令写进 confirm 桶使其离开 allow）被否：那是**改判不是删除**（curl 会变成显式 confirm 而非回落 default，且污染目标桶语义）。

**决策**：层间合并 = **字段级继承**（低层 = 父类，高层 = 子类）：子层未定义的键整体继承；定义即覆盖。列表值双形态：**数组 = 覆盖定义**（本份就是全部）；**inline table `{ add = [...], remove = [...] }` = 继承低层并增删**。标量（default/precedence/version）写值即覆盖。裸列表、桶词条、标量一台模型统一。

**依据**：

- 程序员零学习成本（类继承直觉：不写 = 继承，写了 = 遮蔽）；「照单继承 / 微调 / 完全换一套」三种意图一套模型表达。
- 显式优于隐式：inline table 是显式引用，配置最终效果基本可从本文件读出；「默认合并」下低层未来新增命令会隐式漏进高层效果，审阅需带着低层读。
- TOML 原生支持一个键的值取数组或 inline table 二选一，零新语法；`remove` 键消除前缀歧义，flag 桶从此支持剔除。

### 被否决的替代方案

> [!CAUTION] 【已否决】 被否决的替代方案
> 原因：详见下列各项
>
> - **token 级合并（高层胜出、低层补齐）为默认语义**：「未提及即补齐」隐式依赖低层，整表覆盖难表达；与「同 token 双桶靠 precedence 兜底」边界模糊。
> - **列表内 `super`/`-token` 保留字**：`"super"`、`"-curl"` 带引号混在数组里与命令词条视觉同类；`-` 前缀与 flag 词条（天然 `-` 开头）歧义，flag 桶无法支持剔除。
> - **挪桶表达删除**：挪桶是改判不是删除——写入 confirm 桶后语义变为「显式 confirm」而非「回落 default」（default ≠ confirm 时结果不同），且污染目标桶。

**影响**：design.md 原「merge 语义（token 级）」节整体替换；更正登记第 3 条追加再修订记录。

## D-03 损坏重生成收窄

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「零内置策略与默认配置生成（定稿）」](design.md#零内置策略与默认配置生成定稿) |

**背景**：2026-09-04 定稿「损坏 ≠ 缺失：留档 `.bak-<时间戳>` 后重新生成默认」。设计评审发现该方案与编辑工作流冲突：serve 空闲退出后冷启动遇到用户手改中间态（语法未完成的保存）→ 原文件被静默改名 + 默认模板接管 → 裁决行为整体漂移且用户无感知，反复保存还会堆积 `.bak`。serve 运行中改坏无碍（旧快照保留），风险集中在冷启动路径。

**决策**：收窄为——**仅文件不存在（三层皆缺）才生成默认**；文件存在但解析失败 → stderr 告警 + 按 fail-safe confirm 兜底，**原文件不动、不留档不生成**。

**依据**：

- fail-safe confirm 本身已是安全且保守的工作状态（不误放行），不需要靠「换默认配置」来恢复可用性。
- 保留现场（坏文件原样）利于用户看到并修复自己的语法错误；改名接管反而销毁上下文。
- 生成触发严格限定为「从零引导」场景，与「三层皆缺才生成」的原意对齐。

**影响**：design.md 零内置节条目就地修订 + 更正登记第 7 条；`cairn/zero-builtin-policy-seeding.md` 同步更正。

## D-04 precedence 与 lint 的分工

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「rules.toml 结构（草案）」查表顺序条](design.md#rulestoml-结构定稿) |

**背景**：用户提问「上了配置冲突检查（lint）后，还需要桶间优先级（precedence）吗，纳入冲突检查更好还是保留检查顺序更好」。讨论确认 precedence 的默认序（deny > confirm > allow，default 恒链尾）无分歧，问题在 lint 是否使其冗余。

**决策**：**两者互补，不互相替代**——保留 precedence（可调键不变），lint 并存。lint 上线后 precedence 的角色从「同 token 双桶的静默兜底」收窄为「合法多命中的合成规则」：同文件同 token 双桶由 lint 告警暴露（按 precedence 取生效桶），而运行时的多命中合成永远按 precedence。

**依据**：lint 只能静态查出「同 token 写进多个桶」这一类配置错误；运行时还存在 lint 不报的**合法多命中**——同一命令的不同维度 token 各自命中不同桶（`git show --output=x`：`show` 命中 allow.sub、`--output` 命中 confirm.flag，两条配置各自合法），必须有序合成出唯一裁决；复合命令的组合裁决（任一 deny → deny）也是同一优先序的运行时体现。

### 被否决的替代方案

> [!CAUTION] 【已否决】 以 lint 取代 precedence
> 原因：合法多命中（不同维度 token 命中不同桶）不是配置错误，lint 查不出，无优先序则无合成规则
>
> 删除 precedence 后，`git show --output=x` 型多命中与复合命令组合裁决都失去裁决依据，只能引入更复杂的规则（如「flag 桶仅在 sub 未命中时生效」）来补，复杂度更高。

**影响**：design.md「rules.toml 结构」新增「precedence 与 lint 的分工」条；lint 规则集（结构类）登记「同 token 多桶」规则。

**更正（2026-09-06，实现核实）**：依据段「复合命令的组合裁决（任一 deny → deny）也是同一优先序的运行时体现」措辞过强——实现（`model::Verdict::combine`）把组合裁决**硬编码**为 deny > confirm > allow 的固定序，不随可调 `precedence` 键变化（组合语义是「任一危险即保守」安全性质的组成部分，不开放配置）。precedence 可调性的作用域 = 同命令多维度 token 的查表合成；两者分工不同，非同一机制的两次体现。

## D-05 guard.py 定位重置（参考对象而非验收标准）

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「判定表」定位澄清](design.md#判定表纯语义可-11-平移) |

**背景**：设计评审第一轮以「与 guard.py/engine.rs 判定表不一致」为偏差标准指出默认包问题；用户纠正——本项目与对照脚本本来就是两个东西，guard.py 不是本项目的验收标准，只是参考对象、灵感来源与后续要替换的对象；其中真正值得重视的是等价方言与双桶冲突这类**命令语义问题**（已由 [D-01](#d-01-命令知识库框架) 承载）。

**决策**：guard.py 及其 89 条回归用例定位 = **语义参考、灵感来源与待替换对象，非验收标准**；默认包与回归用例断言冲突时，以定稿草案为准更新用例并留变更记录。

**依据**：

- 默认包存在多处**有意偏离** guard.py 的决策（cargo/go 收窄为命令节、`git reset` 档位、flag 拆 confirm.flag/deny.flag）——以 guard.py 为标准会把这些有意变更误判为回归。
- 回归用例是语义载体而非真理：语义的权威源是定稿草案，用例跟随草案演进并留变更记录，可追溯性由 git 与变更记录承担。

**影响**：design.md 判定表节追加定位澄清；零内置节「测试落点」措辞修正；ROADMAP P3 验收措辞同步（「89 用例全绿」附「断言冲突时以定稿草案为准更新用例留变更记录」）。

## D-06 单命令建模完备性标准

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「单命令建模（定稿）」](design.md#单命令建模定稿) |

**背景**：用户提问「一个命令结构中还有别的部分吗，现有槽位足够描述单一命令了吗（不考虑拼接）」。逐部分盘点发现两个真实缺口（flag 带值形态、位置参数计数语义），同时确认大量部分本就不该知识库管（路径形态、env 前缀、重定向、参数内容模式、未知命令）。

**决策**：完备性标准 = **槽位跟着消费机制走**——一个维度只有存在明确消费者（归一 / lint / 脚本数据源）才配拥有槽位；没有消费者的维度（联网、平台差异）不设，等真实策略需求出现再加且须登记消费机制。据此 v1 槽位封闭为 10 个（补入 `takes_value`、`write_arg_count`），单命令其余部分的责任分工表入 design.md。

**依据**：无消费者的属性是记了没人读的死数据；标准可裁定（每提出一个新槽位都能回答「谁消费它」），防止知识库百科全书化膨胀、间接守住「谓词封闭」。

### 被否决的替代方案

> [!CAUTION] 【已否决】 知识库百科全书化（按「描述命令的一切」建槽位）
> 原因：没有消费机制的维度记了没人读；槽位集合不可裁定，最终演化成绕过零内置策略的隐性规则系统
>
> 网络访问/平台差异/幂等性等维度在出现引用它们的策略或 lint 规则之前不设槽位。

**影响**：知识库槽位表定稿 10 个；design.md 新增「单命令建模」节（分工表一表回答「什么进知识库、什么不进、为什么」）。

## D-07 裁决日志默认开与落盘形态

| 状态 | 日期 | 规范位置 |
|---|---|---|
| 已决策 | 2026-09-06 | [design.md「日志」](design.md#日志格式先行开关位置-p4-定) |

**背景**：M4.3 落地裁决日志，「日志默认开关」是 P4 唯一实现期定点（用户预授权按建议默认开）。落盘位置、时间戳形态、热重载信号的消费时机需就地定。

**决策**：

- **默认开**（安全审计优先：日志自证 `kb` 状态与放行面，关闭是显式行为）；`CRUSH_TETHER_LOG=0|off|false` 关闭。
- 落盘 = `<project>/.crush-tether/decisions.jsonl` 追加写；serve 单点写 + hook 降级/check 自写（同一文件）。写入失败静默——日志永不影响裁决路径。
- `ts` 用 UTC RFC3339（std 无本地时区能力，不为此引依赖）；人读视图由后续 `log` 子命令渲染。
- 热重载信号在 serve 主线程的**请求间隙**消费（RuleSet 含 rhai Engine 非 Send，重编译留主线程）——改规则后的第一个请求触发重载，在途请求不受影响。
- v1 `source.layer` 溯源经合并层 Provenance 映射携带，词表 global/user/project/explicit/default/script；**实现核实（2026-09-06 审查修复）**：explicit（`--config` 经 LayerLabels 换标签）/ script（激活改判时换源）已接线，default 两档可达，**global 值 v1 不可达**（全局层无发现路径，ROADMAP M2.2 已更正登记）——词表按「已定义、待全局层落地」理解。

**依据**：审计自证是零内置策略的配套性质（kb/source 字段让「谁放行、依据什么」可追溯）；默认开与 fail-safe confirm 同方向（多留痕优于少留痕）；UTC 换取零依赖。

### 被否决的替代方案

> [!CAUTION] 【已否决】 日志默认关（隐私优先）
> 原因：裁决日志只含命令与裁决元数据，不含输出内容；默认关会让「零内置策略是否被绕过」无法自证，安全收益大于隐私顾虑（命令本身已在 agent 会话日志中）
>
> 用户可用 `CRUSH_TETHER_LOG=off` 显式关闭，属知情选择。
